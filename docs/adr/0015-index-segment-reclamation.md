# ADR-0015：索引段的回收判定与归属

- **状态**：已接受
- **日期**：2026-11-05

## 背景

[06 §5.3](../chatgpt/06-index-recovery.md) 指出索引段不能沿用对象的 GC 六条件（[03 §8](../chatgpt/03-consistency-kernel.md)），理由是那六条是为**对象 extent** 设计的：

| 六条件 | 为什么套到索引段上不成立 |
|---|---|
| (1) 版本全部 `Obsolete` | 索引条目没有版本状态机 |
| (2) 无存活快照引用 | 索引段从不被快照「引用」，它被「覆盖判定」使用 |
| (3) 无活跃 `PlacementEpoch` 引用 | 索引段没有 epoch 引用 |
| (4) 不在任何 checkpoint 读集 | 段本身**不在**检查点覆盖内（[06 §5.2](../chatgpt/06-index-recovery.md)） |
| (5) 不在未完成迁移的 source/target | 迁移对索引透明（[06 §5.4](../chatgpt/06-index-recovery.md)） |
| (6) WAL 侧无恢复依赖 | 段的发布依赖 `IndexManifest`，与 WAL 截断的关系由 [ADR-0013](0013-index-manifest-in-wal.md) 的 T4 单独处理 |

结果：前五条在索引段上**永远为真**（没有这些东西可以引用），第六条另有规则。若照搬六条件，索引段会被立即判定可回收——**边写边删**，比不回收更糟。反过来，若不回收，索引空间只增不减。

06 只给出了方向（「逐条目快照可见性 + 基线段保护」），并指出两个实现选项：索引层自己实现一个段回收器，或把它做成 `Reclaimer` 的受限子职责。后者会改动 [04 §10](../chatgpt/04-kernel-interfaces.md) 的冻结契约，需要一条 ADR——就是这一条。

还有一个 06 明确指出「本身没有定义清楚」的东西：**基线段（baseline segment）**的豁免。豁免不定义清楚，回收器就无法实现。

## 决策

1. **索引段回收器归索引层，不进内核 `Reclaimer`。**

   [04 §10](../chatgpt/04-kernel-interfaces.md) 的 `Reclaimer` 契约**不变**。理由有三条：

   - **对象不同**：`Reclaimer` 回收的是物理 extent 与映射，索引段回收的是内核之外的文件与段清单条目；
   - **判据不同**：见背景的表格，六条件在索引段上没有区分能力；
   - **依赖不同**：段回收需要「逐条目的快照可见性判定」与「段清单的原子摘除」，这两件事在索引层（协调区 + 段清单）里才有，内核看不到。

   索引层需要内核提供的**唯一**输入是**存活快照集合**（见决策 4）。

2. **回收判定是逐条目的，但回收动作是整段的。**

   ```
   reclaimable(seg) :=
       (G1) seg.id != index.baseline_segment_id            // 非基线段
     ∧ (G2) seg.to_lsn <= index.watermark                  // 段已被水位覆盖（不超前于已发布进度）
     ∧ (G3) ∀ entry ∈ seg.entries:                         // 逐条目：对所有存活快照不可见
              ¬∃ s ∈ live_snapshots: visible(entry, s)
     ∧ (G4) ∀ tomb ∈ seg.tombstones:
              ¬∃ s ∈ live_snapshots: visible(tomb, s)       // 墓碑也不可回收（否则删除复活）
     ∧ (G5) seg 不在任何 Recovered 查询的引用集中           // 见决策 5
     ∧ (G6) seg 已从 index 的段清单中原子摘除                // 先摘链，后删文件
   ```

   六条必须**合取**，没有捷径。逐条理由：

   - **G1 基线段**：新建索引时全部条目都落在基线段里。若允许回收基线段，新建索引的第一次 GC 就会把整个索引导空，而 [06 §3.1](../chatgpt/06-index-recovery.md) 的覆盖判定（`S.xmin ≤ tx_w`）仍会说「完整」——静默返回空结果。

     基线段有**继任者才可回收**：「`index.baseline_segment_id` 已被更新的一条基线段取代，且新基线段已发布到协调区」。这要求索引层显式维护 `baseline_segment_id` 这个字段（当前只在文档的散文里提到「基线段」，没有落成元数据字段，这是 06 §5.3 自己承认的缺口，本 ADR 补上）。

   - **G2 `to_lsn ≤ index.watermark`**：防止回收「尚未被水位覆盖」的段——那种段可能还在发布流程中间（段已 fsync、协调区未更新，[06 §5.1](../chatgpt/06-index-recovery.md) 的第四行）。

   - **G3 逐条目**（06 §5.3 的核心）：不看段的 LSN 区间，只看条目里的 `(object_id, version_id, created_by_xid, deleted_by_xid)` 对所有存活快照的可见性。用一个创建于 LSN 100、此后从未更新的对象举例：它的唯一条目在覆盖 `[0, 500]` 的段里，按区间回收会让 LSN ≥ 500 的快照读不到它。

   - **G4 墓碑**：墓碑不可见性独立判定。若墓碑被回收而删除前的条目还在，就会出现「删除复活」（[06 §2.6](../chatgpt/06-index-recovery.md)）。注意两个方向相反：**新快照需要墓碑**，**旧快照需要删除前的条目**——回收器必须两个方向都判，不能合成一条。

   - **G5 引用集**：见决策 5。

   - **G6 先摘链再删文件**：与 [03 §8](../chatgpt/03-consistency-kernel.md)「先注销引用、再释放物理空间」完全同源。反过来会出现「查询拿到一个即将被删的段的指针」。

3. **不做部分回收；需要部分保留时走合并（compaction）。**

   段是不可变的，**不存在「删掉段里的一半条目」这个操作**。段内只要有一条目仍可见，整段保留。

   这带来空间放大：一个段里 99% 的条目已不可见，却因为 1% 存活而无法回收。解法是合并再回收，而不是部分删除：

   ```
   1. 选择满足「存活条目占比 < 阈值」的段（阈值是域配置，不冻结）
   2. 把其中仍可见的条目与墓碑重写进新段（新段是新文件，走 §2.4 的段发布流程）
   3. 新段发布到协调区，且 index.watermark 覆盖旧段区间
   4. 旧段满足 G1–G6 → 回收
   ```

   合并是**空间换空间**：一次多写一个新段，换回收一个旧段。它必须复用 [06 §2.4](../chatgpt/06-index-recovery.md) 的发布流程（段先于水位、幂等键、CAS 单写者），不得另走一条更短的路径——否则「先段后水位」这条最关键的规则就有了例外。

4. **内核提供给索引层的唯一回收输入：一个快照集合读取入口。**

   ```rust
   /// 内核 → 索引层的只读输入：当前存活快照集合（快照引用计数 > 0）
   pub trait LiveSnapshotSource {
       /// 枚举当前存活快照
       fn live_snapshots(&self) -> KernelResult<Vec<Snapshot>>;
       /// 判定某个 (created_by_xid, deleted_by_xid) 对给定快照是否可见
       /// 必须复用 TransactionManager::visible 的同一实现，不得复制
       fn visible(&self, entry: &EntryVisibility, snap: &Snapshot) -> bool;
   }
   ```

   - **`visible` 不得由索引层实现。** 索引层复制的可见性判定是 06 §6.1 的 A1 断言（「不读 LSN、不读 VersionId、不读时间戳」）唯一可能被破坏的地方。内核提供同一个实现，索引层只调用。
   - **`EntryVisibility` 只含 xid 与版本标识**（`created_by_xid` / `deleted_by_xid`），不含 payload、不含物理位置（[04 §14.1 规则 1](../chatgpt/04-kernel-interfaces.md)）。
   - 本 trait 随 `ChangeFeed` 一并进入冻结清单（[ADR-0012](0012-changefeed-freeze.md) 的 F16 之后新增 F17），因为它的输出参与正确性判定。

5. **G5 的实现：epoch 式引用注册，而不是「无引用即回收」。**

   查询在索引段上持有读引用，回收器必须排除这些段。第一版做法：

   ```
   1. 回收器推进一次回收代次 reclaim_gen（原子递增）
   2. 等待所有进程确认（与 03 §8 的「空闲 PlacementEpoch」同构）
   3. 采样 live_snapshots 与已注册的段引用集
   4. 在 (2) 之后开始的读只能看到新段清单 → 不会引用被回收的段
   ```

   这条与 [03 §8](../chatgpt/03-consistency-kernel.md) 的 GC 竞态处理**同一条原则**：判定必须在一个快照式视图上做。索引层复制的是这套流程的形状，不是它的条件。

6. **与对象 GC 无顺序依赖，但条件同源。**

   对象 extent 的回收（`Reclaimer`）与索引段回收都以「存活快照集合」为准（对象侧的六条件 (2)、索引侧的 G3/G4）。因此不存在「索引还指着已回收对象」的窗口——旧快照只要还活着，两侧都保留它需要的东西。

   **不引入跨模块的回收顺序协调**：加一个「先回收索引、再回收对象」的顺序会制造一个假的依赖（两者互不读取对方的存储），并让一个模块的停滞阻塞另一个。

7. **回收器不得读时钟判定。**

   [04 §2.6 C5](../chatgpt/04-kernel-interfaces.md) 禁止内核直接读时钟，本 ADR 把同一要求延伸到索引层回收：条目年龄、段年龄一律由**快照存活期**（存活快照集合的变化）表达，不由墙钟表达。理由是 [06 §6.1 A8](../chatgpt/06-index-recovery.md) 的要求：同一批 WAL 记录重放两次必须得到相同的水位——若回收依赖时钟，重放的结果就不可复现。

## 备选方案

1. **复用内核 `Reclaimer` 与六条件** → 前五条在索引段上恒真，段会被立即回收（边写边删）；且六条件根本表达不了「逐条目快照可见性」。改为索引层自己的判定。
2. **把索引段回收做成 `Reclaimer` 的受限子职责** → 要改 [04 §10](../chatgpt/04-kernel-interfaces.md) 的冻结契约，而这个契约的语义是「物理 extent 与映射」，塞进内核之外的段文件类型会让 `Reclaimer` 同时依赖索引层类型。改为索引层负责。
3. **按段的 LSN 区间回收**（「比 `min_required_lsn` 老的段都可以删」）→ 06 §5.3 的反例：创建于 LSN 100、从未更新的对象会从新快照里消失，而覆盖判定仍报「完整」。改为逐条目。
4. **基线段永久豁免（不设继任者条件）** → 索引重建一次就泄漏一个基线段，重建多次后空间线性增长。改为「有已发布的继任基线段才可回收」。
5. **允许部分回收（段内删除部分条目）** → 段是不可变文件，部分删除要么破坏 CRC/摘要，要么退化成原地重写（等于每次回收都做一次合并）。改为整段回收 + 显式合并。
6. **部分保留时直接原地重写段文件** → 违反「已发布段不被修改」（[06 §2.5](../chatgpt/06-index-recovery.md) 幂等性的第一条依据），正在读该段的查询会看到撕裂内容。改为新段 + 发布 + 旧段回收。
7. **索引层自己实现可见性判定** → 06 §6.1 A1 断言唯一可能被破坏的地方；两份判定迟早分叉。改为内核提供 `visible`。
8. **用「引用计数为 0」代替存活快照集合** → 索引条目没有稳定的引用计数（它按快照动态可见），计数会与可见性判定分叉。改为存活快照集合 + 回收代次。
9. **用时钟（条目年龄 > TTL）判定回收** → 与 A8（重放同一批 WAL 得到相同水位）冲突，且重启后结果不确定。改为快照存活期表达。
10. **规定「先回收索引段、再回收对象 extent」的顺序** → 制造一个假的跨模块依赖，一个模块停滞会阻塞另一个。改为条件同源、互相独立。

## 后果

**正面**

- 索引空间终于有了一条可执行、可测试的回收路径，且不再有「边写边删」的风险。
- 「基线段」从一个散文概念变成元数据字段（`baseline_segment_id`），06 §5.3 承认的缺口被补上。
- 可见性判定只有一份实现（内核的 `visible`），索引层不可能出现第二套口径。
- 对象与索引的回收互不阻塞，排障时不需要同时看两个模块的状态。

**负面**

- 索引层需要长期保存存活快照集合的读取能力，因此内核必须暴露 `LiveSnapshotSource`（新增冻结项）。
- 逐条目判定让回收的 CPU 成本与段大小成正比；第一版没有增量结构，大段回收会慢。
- 合并（compaction）与回收耦合：不做合并，空间回收率受限于「段内存活条目占比」；做了合并，就要多走一遍段发布流程。
- `reclaim_gen` 的「等待所有进程确认」在高并发下可能引入可观测的停顿。

**缓解**

- 逐条目判定的成本可用「段内最早/最新 xid 区间」做快速预筛：若某个段的所有条目的 `created_by_xid` 都大于所有存活快照的 `xmin`，可以直接判定为「全部不可见」，无需逐条。这是纯优化，不改变判定结果。
- 合并的阈值是域配置（[07 §1.2](../chatgpt/07-hardware-resource-management.md) 的同类参数），先取保守值（存活占比 < 30% 才合并），由实测校准。
- `reclaim_gen` 的停顿与 [03 §8](../chatgpt/03-consistency-kernel.md) 的 GC 停顿是同一类代价，两者的代次推进可以合并为一次（减少停顿次数），但仍是两次独立的判定。
- 回收器的正确性由 06 §6.2 的用例族守住，本 ADR 额外要求两条：`segment_gc_keeps_baseline`（基线段不被回收）、`segment_gc_no_partial_reclaim`（段内有任一条目可见时整段保留）。
