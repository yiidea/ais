# ADR-0009：故障注入夹具与不变量可执行化

- **状态**：已接受
- **日期**：2026-11-02

## 背景

[04-kernel-interfaces.md](../chatgpt/04-kernel-interfaces.md) 冻结了接口并给出了一条按编译依赖排序的实现顺序。但那条顺序有一个隐含前提：模块能分别编译通过就算阶段完成。

实际上，前 6 个模块（设备、IoExecutor、WAL、映射、extent、对象）单独看都可以通过单元测试，**只有把它们串成「写入—崩溃—恢复」的闭环，才会暴露真正的问题**：掉电后 WAL 里哪些字节还在、已提交的事务能不能恢复、迁移回滚有没有生效。

而这个闭环在开发机上跑不起来：

- 需要真 NVMe 才有真实的掉电语义；
- 需要真的拔电或 `kill -9` 才能测崩溃时机；
- 偶发的并发交错失败无法复现，也就无法回归。

因此需要一套夹具。这里要解决的关键问题有三个：

1. **夹具用什么形态实现**——是 mock（只验证「调用发生了」）还是模拟器（验证「崩溃后状态是对的」）；
2. **注入点怎么定位**——按「第 N 次系统调用后 kill」还是按语义位置；
3. **不变量是 CI 跑一次还是常驻**。

前两个问题在 [03 §11.3](../chatgpt/03-consistency-kernel.md) 里只给了方向（「用一个 FaultInjector 包装所有 write / flush / rename，按第 N 次调用后 kill」），没有定死形式。第三个问题在 [04 §14.2](../chatgpt/04-kernel-interfaces.md) 里被列为 CI 检查项，但没说清它是不是常驻的。

这三件事都会约束实现，一旦有第二个实现者就必然产生分歧，因此需要记录决策。

**本 ADR 对 [ADR-0008](0008-kernel-interface-freeze.md) 的修订**：新增冻结项 F15（`Clock`，见 [04 §1.2](../chatgpt/04-kernel-interfaces.md)）与 [04 §2.6](../chatgpt/04-kernel-interfaces.md) 的 C5 / C5.1 / C5.2。修订理由是决策 9：夹具的确定性要求内核不直接读真实时钟。其余冻结项（F1–F14）不变。

## 决策

1. **夹具是模拟器，不是 mock**。假设备必须实现完整的设备语义，尤其是**区分「写到了」与「写到了并且活过了掉电」**——易失缓存与持久介质分离建模，`flush(None)` / `flush(Write)` / `flush(Durable)` 三个耐久等级严格区分（对应 [04 §4.2 E1](../chatgpt/04-kernel-interfaces.md) 与 §6.1 D2 的设备侧动作）。

   **持久介质必须是文件支撑的，不能是内存**：崩溃恢复层要重启进程并用同一份目录恢复，介质在内存里会让所有恢复用例空跑。

   落盘内容与真实设备的对拍是发布前的必需项；对拍必须区分**进程崩溃**与**掉电**两个失效域（`kill -9` 不丢 OS page cache，真断电才丢），用错方法会得到「假设备是对的」的错误结论。

2. **注入点以语义 site 为主键，调用序号为修饰符**。内核在关键位置显式打点（`wal.frame.partial`、`mapping.switch.after_log` 等），而不是靠拦截设备调用推断位置。裸的「第 N 次调用」注入只用于探索性测试，不进回归用例。

   理由：序号注入在重构后会漂移到别处，测试可能悄悄失去覆盖而不报错——这是比没有测试更坏的情况。

3. **注入 site 分两类，两套打点机制，不可混用**：

   | 类别 | 判定 | 机制 | 顺序由谁保证 |
   |---|---|---|---|
   | **设备级** | 对应一次设备操作 | 由 `IoExecutor` 承载（操作携带 site 标签） | 真实 I/O 顺序 |
   | **内核级** | 不对应任何设备操作 | 模块内显式打点 `fault_point!` | 内核逻辑顺序 |

   理由：早先的表述是「打点集中在 `IoExecutor` 一层，因为打点顺序必须与真实 I/O 顺序一致」——**这个理由只对设备级 site 成立**。GC 摘链、内存版本发布、事务提交点这些内核级 site 根本不对应设备操作，塞进 `IoExecutor` 是不可能的；硬塞的后果是注入点的触发时机变成「下一次设备操作时」，测试会「通过」但什么都没测到。

   设备级 site 在 `IoExecutor` 上的具体形状（标签放 `DeviceOp` 上还是放 `submit_and_wait` 的参数上、批量接口怎么给每个操作打标签）需要一条补充 ADR。

4. **崩溃注入用真正的进程退出模拟**，不用 `panic!`（会 unwind、跑 `Drop`、释放锁）与 `abort`（留下难以断言的 core dump）。被测进程以非零码退出后由驱动器重启同一目录走恢复流程。

   「已确认提交」的记录写在被测进程之外，由驱动器持有——内核不得自己写这份记录；该记录必须显式 `fsync`，并采用「追加式 + 每条带 CRC」的格式，以容忍崩溃时的半截尾记录。

5. **不变量全部常驻**：`INV1`–`INV5` 与架构 `I1`–`I6` 十一条都在 `feature = "invariants"` 下常驻——既在每次 CI 中断言，也在长时间运行的 fuzz / soak 中持续断言。其中依赖设备行为的 `INV2`、`INV5`、架构 `I1`/`I5`/`I6` **额外**由每一个崩溃注入用例断言（它们既是常驻检查项，也是 L2 用例的通过条件）。

   架构 `I6`（DRAM / GPU HBM 不是最终持久存储）**另外必须由真机断电对拍兜底**，不能只靠假设备断言——假设备本身就是被测模型，只用它验证自己等于没验证。

6. **一致性检查器独立于内核实现**：它从底层存储（WAL 段、checkpoint 目录、映射表）**重新构建**对象视图，再与内核报告的状态和外部确认日志三方比对。用内核自己的 API 重建状态，验证出的只是「内核自洽」。

   判定采用差异集（`DiffSet`）而非逐项相等：允许的差异只有「注入点之后未提交的事务」，任何其他差异都是失败。

   **与 [ADR-0008](0008-kernel-interface-freeze.md) 冻结的 K3 的关系**：`RecoveryManager::verify` 是**内核内**唯一的校验实现；本决策的外部重建器是**测试专用**的、位于内核之外的实现。二者不互相替代：`verify` 检查内核自认为的状态是否自洽（引用计数、epoch、状态机），外部重建器检查磁盘上实际有什么与内核的认知是否一致。缺了外部重建器，「内核自己不知道自己丢了什么」这类缺陷无法被发现。

7. **夹具受公共 API 约束**：假设备实现 `StorageDevice`——那是 [04 §14.1 规则 3](../chatgpt/04-kernel-interfaces.md) 允许外部实现的那一个 trait，因此它天然工作在物理位置上。规则 1 允许物理类型出现在这类内部 trait 上，但**不允许出现在对外导出的表面上**。所以夹具类型整体放在 `#[cfg(feature = "test-harness")]` + `#[doc(hidden)]` 模块下，发布构建中整个模块不存在，不进入 `cargo public-api` 快照。

8. **夹具不得自动重试、不得吞错误、不得 panic**。内核「不自动重试」的契约只有在夹具稳定产生 `Io` / `Retryable` 错误时才测得到；夹具一旦「贴心」地重试，这条契约永远测不到。

9. **夹具的确定性是硬要求**：同一个 seed + 同一注入序列必须得到同一结果。夹具内禁止真实随机源、真实时钟与哈希迭代顺序依赖。

   内核中所有时间读取必须经过 `Clock` trait（`Clock` 作为 [04 §1.2](../chatgpt/04-kernel-interfaces.md) 冻结清单的新增项 F15 记入，依据是本 ADR 的修订说明；约束细节见 [04 §2.6](../chatgpt/04-kernel-interfaces.md) 的 C5 / C5.1 / C5.2），真实时钟调用由 lint 拦截。`Clock` 返回相对单调纳秒而非 `Instant`——`Instant` 无法在稳定版 Rust 上任意构造，假时钟实现不了「推进到任意时刻」。

## 备选方案

1. **只用 mock 设备** → 验证「调用发生了」而不是「崩溃后状态是对的」，掉电语义完全没测到，而掉电正是本设计最核心的风险。
2. **介质放在内存里** → 崩溃后重启读到空目录，所有恢复用例空跑，测试体系整体失效。
3. **只在真机上做崩溃注入**（拔电 / `kill -9`）→ 能测真东西，但无法在每次 PR 上跑，无法在 CI 里回归，且真机崩溃时机会随负载变化，不可复现。
4. **沿用「第 N 次调用后 kill」**（[03 §11.3](../chatgpt/03-consistency-kernel.md) 的原建议）→ 实现最简单，但重构会让注入点漂移。折中是保留序号作为修饰符，语义 site 才是主键。
5. **所有 site 都塞进 `IoExecutor`** → 内核级 site 无处安放，硬塞会让触发时机漂移到下一次设备操作，测试「通过」但什么都没测到。
6. **在各模块内部各自打点** → 打点顺序与真实 I/O 顺序脱钩，设备级注入点的语义不可靠。
7. **用 `panic!` 模拟崩溃** → 会 unwind，会跑 `Drop`，可能把锁释放掉；测出来的恢复路径与真实崩溃不是一回事。
8. **用内核 API 做一致性检查** → 只能验证自洽，验证不了「内核漏写了一个对象但自己不知道」。
9. **不变量只在 CI 跑一次** → 长时间运行中的状态漂移（引用计数、epoch 推进、迁移回滚遗漏）测不出来，而这些恰恰是长期运行后才出现的问题。
10. **用 `kill -9` 验证掉电语义** → `kill -9` 不丢 page cache，未 fsync 的数据在进程被杀后仍在，与假设备的模型不一致；用错失效域会得出「假设备错了」的错误结论。

## 后果

**正面**

- 第一版内核可以在没有真 NVMe / GPU 的机器上完整跑通「写入—崩溃—恢复」闭环。
- 崩溃时机精确到语义位置，测试在重构后仍然有效。
- 不变量从「文档里的断言」变成「常驻代码里的检查」，长期运行的状态漂移可被捕获。
- 假设备与真机的对拍提供了「模拟器语义正确」的外部证据，避免在错误的世界里验证内核。
- 故障注入点目录本身是设计文档的一部分——它把「崩溃会怎样」写成了可执行的期望。

**负面**

- 前期投入不小：假设备 + 注入器 + 驱动器 + 检查器是一个独立的工作包。
- 夹具本身是代码，也会有 bug；对拍机制是必需的额外成本。
- 语义 site 意味着内核要在关键位置埋点，增加实现负担与噪声（虽然由 feature 门控）。
- 设备级 site 需要 `IoExecutor` 承载标签，是对已冻结契约的补充，需要一条 ADR。
- 确定性调度器是最大的单项工作，若要做性质测试还需额外投入。

**缓解**

- 夹具按「先假设备 → 注入器 → 驱动器 → 检查器」的顺序增量交付；检查器完成前，L2 结论只对假设备有效，不对内核背书。
- 打点由 feature 门控并按两类分开实现，对正常路径的运行时开销可忽略。
- site 目录用枚举 + 穷尽 `match` 做编译期校验，新增 site 未登记即编译失败。
- 确定性调度器可以推迟：先用单线程 workload + 少量并发用例把 L2 跑起来。
- 对拍的失效域被明确区分，掉电语义对拍每周在实验机上跑，作为发布前置条件而不是每次 PR 的负担。
- 允许新增错误变体（`#[non_exhaustive]`）与带默认实现的 trait 方法，避免小改动也要走 ADR。
