# ADR-0009：故障注入夹具与不变量可执行化

- **状态**：已接受
- **日期**：2026-11-02

## 背景

[04-kernel-interfaces.md](../chatgpt/04-kernel-interfaces.md) 冻结了接口并给出了一条按编译依赖排序的实现顺序。但那条顺序有一个隐含前提：模块能分别编译通过就算阶段完成。

实际上，前 6 个模块（设备、IoExecutor、WAL、映射、extent、对象）单独看都可以通过单元测试，**只有把它们串成「写入—崩溃—恢复」的闭环，才会暴露真正的问题**：掉电后 WAL 里哪些字节还在、已提交的事务能不能恢复、迁移回滚有没有生效。

而这个闭环在开发机上跑不起来：

- 需要真 NVMe 才有真实的掉电语义；
- 需要真的拔电或 `kill -9` 才能测崩溃时机；
- 偶发的并发交错失败无法复现，也就无法回归。

因此需要一套夹具。这里要解决的关键问题有三个：

1. **夹具用什么形态实现**——是 mock（只验证「调用发生了」）还是模拟器（验证「崩溃后状态是对的」）；
2. **注入点怎么定位**——按「第 N 次系统调用后 kill」还是按语义位置；
3. **不变量是 CI 跑一次还是常驻**。

前两个问题在 [03 §11.3](../chatgpt/03-consistency-kernel.md) 里只给了方向（「用一个 FaultInjector 包装所有 write / flush / rename，按第 N 次调用后 kill」），没有定死形式。第三个问题在 [04 §14.2](../chatgpt/04-kernel-interfaces.md) 里被列为 CI 检查项，但没说清它是不是常驻的。

这三件事都会约束实现，一旦有第二个实现者就必然产生分歧，因此需要记录决策。

## 决策

1. **夹具是模拟器，不是 mock**。假设备必须实现完整的设备语义，尤其是**区分「写到了」与「写到了并且活过了掉电」**——易失缓存与持久介质分离建模，`flush(None)` / `flush(Write)` / `flush(Durable)` 三个耐久等级严格区分。落盘内容与真实设备的对拍是发布前的必需项。

2. **注入点以语义 site 为主键，调用序号为修饰符**。内核在关键位置显式打点（`wal.frame.partial`、`mapping.switch.after_log` 等），而不是靠拦截设备调用推断位置。裸的「第 N 次调用」注入只用于探索性测试，不进回归用例。

   理由：序号注入在重构后会漂移到别处，测试可能悄悄失去覆盖而不报错——这是比没有测试更坏的情况。

3. **打点集中在 `IoExecutor` 一层**，由 `feature = "fault-injection"` 门控。内核各模块不各自埋点。

   理由：打点顺序必须与真实 I/O 顺序一致。若 `ExtentManager` 与 `WalManager` 各自打点，两者的先后关系取决于代码结构而非实际 I/O 时序，注入点的语义就不再可靠。

4. **崩溃注入用真正的进程退出模拟**，不用 `panic!`（会 unwind、跑 `Drop`、释放锁）与 `abort`（留下难以断言的 core dump）。被测进程以非零码退出后由驱动器重启同一目录走恢复流程。「已确认提交」的记录写在被测进程之外，由驱动器持有——内核不得自己写这份记录。

5. **不变量断言分为两类**：
   - 结构性不变量（INV1、INV4、I3、I4 等）与不依赖设备行为的断言，在**常驻**检查中开启（`feature = "invariants"`），在模糊测试与 soak 中持续断言，而不是只在 CI 跑一次；
   - 依赖设备行为的不变量（INV2、INV5、I2、I5、I6）由崩溃注入用例覆盖，每个用例都断言。

6. **一致性检查器独立于内核实现**：它从底层存储（WAL 段、checkpoint 目录、映射表）**重新构建**对象视图，再与内核报告的状态比对。用内核自己的 API 验证内核自己的不变量，只会验证出「内核自洽」。

   判定采用差异集（`DiffSet`）而非逐项相等：允许的差异只有「注入点之后未提交的事务」，任何其他差异都是失败。

7. **夹具受公共 API 约束**：夹具类型放在 `#[cfg(feature = "test-harness")]` + `#[doc(hidden)]` 模块下，发布构建中整个模块不存在，不进入 `cargo public-api` 快照（否则会与 [ADR-0008](0008-kernel-interface-freeze.md) 的「公共表面不含物理标识符」冲突——假设备天然工作在 `PhysicalLocation` 上）。

8. **夹具不得自动重试、不得吞错误、不得 panic**。内核「不自动重试」的契约只有在夹具稳定产生 `Io` / `Retryable` 错误时才测得到；夹具一旦「贴心」地重试，这条契约永远测不到。

9. **夹具的确定性是硬要求**：同一个 seed + 同一注入序列必须得到同一结果。夹具内禁止真实随机源、真实时钟与哈希迭代顺序依赖。内核中所有时间读取必须经过可注入的 `Clock` trait，真实时钟调用由 lint 拦截。

## 备选方案

1. **只用 mock 设备** → 验证「调用发生了」而不是「崩溃后状态是对的」，掉电语义完全没测到，而掉电正是本设计最核心的风险。
2. **只在真机上做崩溃注入**（拔电 / `kill -9`）→ 能测真东西，但无法在每次 PR 上跑，无法在 CI 里回归，且真机崩溃时机会随负载变化，不可复现。
3. **沿用「第 N 次调用后 kill」**（[03 §11.3](../chatgpt/03-consistency-kernel.md) 的原建议）→ 实现最简单，但重构会让注入点漂移。折中是保留序号作为修饰符，语义 site 才是主键。
4. **在各模块内部各自打点** → 打点顺序与真实 I/O 顺序脱钩，注入点语义不可靠。
5. **用 `panic!` 模拟崩溃** → 会 unwind，会跑 `Drop`，可能把锁释放掉；测出来的恢复路径与真实崩溃不是一回事。
6. **用内核 API 做一致性检查** → 只能验证自洽，验证不了「内核漏写了一个对象但自己不知道」。
7. **不变量只在 CI 跑一次** → 长时间运行中的状态漂移（引用计数、epoch 推进、迁移回滚遗漏）测不出来，而这些恰恰是长期运行后才出现的问题。

## 后果

**正面**

- 第一版内核可以在没有真 NVMe / GPU 的机器上完整跑通「写入—崩溃—恢复」闭环。
- 崩溃时机精确到语义位置，测试在重构后仍然有效。
- 不变量从「文档里的断言」变成「常驻代码里的检查」，长期运行的状态漂移可被捕获。
- 假设备与真机的对拍提供了「模拟器语义正确」的外部证据，避免在错误的世界里验证内核。
- 故障注入点目录本身是设计文档的一部分——它把「崩溃会怎样」写成了可执行的期望。

**负面**

- 前期投入不小：假设备 + 注入器 + 驱动器 + 检查器是一个独立的工作包。
- 夹具本身是代码，也会有 bug；对拍机制是必需的额外成本。
- 语义 site 意味着内核要在关键位置埋点，增加实现负担与噪声（虽然由 feature 门控）。
- 确定性调度器是最大的单项工作，若要做性质测试还需额外投入。

**缓解**

- 夹具按「先假设备 → 注入器 → 驱动器 → 检查器」的顺序增量交付；检查器完成前，L2 结论只对假设备有效，不对内核背书。
- 打点由 feature 门控并集中在 `IoExecutor`，对正常路径的运行时开销可忽略。
- site 目录用枚举 + 穷尽 `match` 做编译期校验，新增 site 未登记即编译失败。
- 确定性调度器可以推迟：先用单线程 workload + 少量并发用例把 L2 跑起来。
- 允许新增错误变体（`#[non_exhaustive]`）与带默认实现的 trait 方法，避免小改动也要走 ADR。
